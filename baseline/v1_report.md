# 아파트 입주 전후 교통 영향·신호 후보 비교 연구 보고서

작성 기준: 2026-11-10 · 합성 데이터 · Python 3.11 / Eclipse SUMO 1.28.0

## 결론

요청한 첫 번째 프로젝트의 구현·합성 실험·재현 기록을 완료했습니다. 입주 전, 입주 후, 신호 조정 후보를 같은 화면에서 비교하고 SUMO를 실제로 실행합니다. 후보가 항상 좋아지는 것은 아니며, 어떤 방향에 불이익이 생기는지와 종료 시점까지 처리하지 못한 차량을 함께 보여줍니다.

이 결과는 현장 교통영향평가를 대체하거나 안전을 보장하지 않습니다. 동생분의 직접 조작·해석·실무 타당성 검토는 아직 확인하지 않았습니다. 그 부분은 소프트웨어 완료와 구분해 포트폴리오 가이드에 남겼습니다.

## 1. 연구 질문과 판정 기준

연구 질문은 “가상 아파트의 추가 수요가 주어졌을 때, 보행·신호 조건을 지키며 녹색 배분을 바꾸면 방향별 부담이 어떻게 달라지는가?”입니다.

목적함수는 구분합니다. 공식 후보 탐색은 네 방향 중 최대 v/c 최소화입니다. SUMO 검증은 완료 차량 평균 시간 손실, 방향별 악화, 미진입·미완료, 실제 통과 수, 신호·보행 동작 이상을 함께 확인합니다. v/c 최적 후보가 SUMO 평균 시간 손실의 최적 후보라는 가정은 하지 않습니다. 모든 후보를 SUMO로 전수 탐색한 것도 아닙니다.

완료 기준은 입력 변경·오류 차단, 세 상황 계산, 도로망·수요·신호 생성, 실제 TraCI 실행, 같은 수요 비교, 결과 저장, 회귀 테스트, 반복·경계 실험, 문서화입니다. 현장 보정·인증·지원자 본인의 경험 증명은 이번 소프트웨어의 완료 기준에 포함하지 않습니다.

## 2. 공개 자료 조사와 선택

| 자료 | 이번에 사용한 부분 | 적용하지 않은 범위 |
|---|---|---|
| FHWA Traffic Signal Timing Manual | 포화교통류율 × 유효녹색 비율의 처리능력 구조 | 한국 법정 평가 기준·LOS 판정 |
| Eclipse SUMO | 도로망, 차량·보행자 이동, 고정 신호, 관측 | 현장 보정, 복잡한 네트워크, 실제 안전 인증 |
| TraCI | 단계별 실행, 활성 신호, 차량·보행자 위치 확인 | 강화학습·적응 신호 제어 |
| UXsim 검토 | 대안 교통 시뮬레이터 조사 | 이번 구현에는 사용하지 않음 |

SUMO를 선택한 이유는 Python에서 제어할 수 있고 차량·보행자 신호 동작을 원시 로그로 점검할 수 있기 때문입니다. 새로 구현한 것은 합성 실험 설계, 입력 검사, 비교 화면, 결과 집계와 검증 절차입니다. 차량 이동 모델 자체를 새로 개발했다고 표현하지 않습니다.

## 3. 데이터와 기본 조건

관측기간의 기존 수요는 북 650·남 550·동 450·서 350대/시간입니다. 추가 수요는 250·150·100·100대/시간으로 총수요가 2,000에서 2,600대/시간으로 증가합니다. 실제 아파트 세대수나 법정 발생률에서 추정한 값이 아닙니다.

네 방향 직진 1차로, 접근로 각 300m, 제한속도 50km/h입니다. 좌·우회전과 주변 교차로 영향은 제외합니다. 진입 차로에 대응하는 반대편 출구 차로를 만들어 의도하지 않은 합류 병목을 피합니다.

입주 전·후 남북/동서 녹색은 40/40초, 기본 후보는 50/30초입니다. 주기 90초, 각 축 황색 3초·전적색 2초입니다. 공식 모델의 차로당 포화교통류율은 1,800대/시간, 출발 손실은 2초로 가정합니다.

준비 900초, 관측 3,600초, 추가 종료 900초입니다. 추가 종료시간에는 새 수요를 생성하지 않습니다. 그러므로 끝까지 밀려 있는 차량이 빠져나가는 시간을 포함한 완료 차량 집계와 관측시간 안의 통과 수를 혼동하면 안 됩니다.

차량 수는 기간별 rate×duration/3600을 반올림한 정수입니다. 기본 실험은 균등 출발, 반복 실험은 고정된 총 차량 수 안에서 시드별 균등 난수 출발 시각을 사용합니다. 포아송 도착 대수나 실측 분포를 재현한 것은 아닙니다. 시간은 0.5초 간격에 맞춥니다. 기존 차량의 ID·출발 시각을 보존하고 추가 차량만 더합니다. 입주 후와 후보는 동일한 after.rou.xml 파일을 사용합니다.

## 4. 계산과 보행 조건

방향별 공식은 c = n × s × (G − L) / C, v/c = v / c입니다. n은 차로 수, s는 차로당 포화교통류율, G는 녹색, L은 출발 손실, C는 주기입니다. 황색·전적색 통과를 처리능력에 포함하지 않는 단순화입니다.

기본 처리능력은 방향당 760대/시간입니다. 50/30초 후보에서는 남북 960, 동서 560대/시간입니다. 최대 v/c는 입주 전 0.855, 입주 후 1.184, 후보 0.982입니다. 이 수치는 공식의 가정상 비율이며 관측 통과량이나 LOS가 아닙니다.

신호 합계는 G_NS + G_EW + 2×(황색+전적색) = 주기를 검사합니다. 보행 필요시간은 진입 허용 + 횡단길이/속도 + 여유이고, 필요시간 ≤ 보행 배정 ≤ 평행 차량 녹색을 검사합니다.

기본 가정은 보행 진입 허용 3초, 가정 길이 20m, 속도 1m/s, 여유 2초로 필요시간 25초입니다. 각 횡단보도에는 60명/시간의 합성 수요를 생성합니다. 진입 허용 후 보행 신호를 닫고 남은 평행 차량 녹색 동안 이미 진입한 보행자가 횡단하도록 구성합니다.

입력 길이 20m는 보수적인 검사 가정입니다. 생성 도로망의 실제 횡단 길이는 기본 6.4m이며 입력 20m로 도로 형상을 늘리지는 않습니다. 검사에는 입력·생성 길이 중 긴 값을 사용합니다. 실제 이동에는 생성 형상이 적용되므로 20m 횡단 행동을 검증했다고 해석하면 안 됩니다. 보행속도를 0.7m/s로 바꾸면 필요시간은 약 33.57초여서 34초 배정이 필요합니다. 별도 실험에서는 46/34초 후보로 검사와 실행을 확인했습니다.

## 5. 구현 구조

입력 설정 → 단위·범위·합계·보행 검사 → 공식 계산 → netconvert 도로망 생성 → 생성 횡단길이 재검사 → 수요/신호 XML 생성 → TraCI로 3상황 실행 → 원시 결과와 비교표 저장 순서입니다.

실행 중에는 현재 신호가 기대한 현시와 맞는지, 상충 차량 녹색이 겹치는지, 보행 신호 및 횡단 중 보행자와 상충 차량 녹색이 겹치는지, 적색 진입이 관측되는지를 확인합니다. SUMO 충돌 관측과 차량 텔레포트도 집계합니다. 검사는 0.5초 샘플링 범위이며 현실 안전 검토를 대신하지 않습니다.

차량 텔레포트는 비활성화하고 미진입 차량을 버리지 않도록 했습니다. 시나리오당 300초의 실제 실행시간 제한과 중단 기능이 있습니다. 실행 실패·취소와 성공 결과를 구분하며 이전 결과가 현재 입력과 다르면 경고합니다.

## 6. 지표 정의

| 화면/파일 지표 | 집계 정의 | 주의점 |
|---|---|---|
| requested / 요청 | 관측기간에 출발 예정인 차량 집단 | 실제 진입과 다름 |

## 8. 해석

기본 실험은 입주 후 평균 시간 손실이 약 20.411초이고 50/30초 후보에서 약 18.380초입니다. 감소는 약 9.95%지만 동·서측 시간 손실은 증가합니다. “모든 방향의 교통을 개선했다”는 결론은 맞지 않습니다.

공식 후보 열거에서 최대 v/c가 가장 작은 배분은 49/31초(최대 v/c 약 0.957)입니다. 이 후보의 SUMO 평균 시간 손실은 약 18.531초로, 50/30초의 약 18.380초보다 조금 큽니다. 목적함수가 다르고 공식 포화교통류율을 SUMO에 보정하지 않았기 때문에 순위가 같을 필요가 없습니다. SUMO 전체 최적해를 찾았다고 주장하지 않습니다.

공식에서 입주 후 북측 v/c가 1을 넘지만 SUMO에서는 종료까지 전 차량이 완료됩니다. 추가 종료시간의 영향과 공식/SUMO 처리 특성의 차이를 함께 고려해야 합니다. 이 불일치를 숨기지 않고 현장 자료 보정의 필요성으로 남깁니다.

고수요 실험에서는 후보의 완료 차량 평균이 조금 작아도 미진입+미완료 차량이 454대에서 490대로 증가합니다. 동서 방향 잔류가 특히 커집니다. 완료된 차량만 평균하면 긴 대기 차량이 빠져 결과가 좋아 보일 수 있으므로, 이 실험은 후보의 전반적 개선으로 판정하지 않습니다. 출발 지연 역시 별도 확인해야 합니다.

| 차량 경로 생성 실패 | 보행 차로가 lane 0인데 자동차 연결도 0부터 지정함. 자동차 차로를 1부터 매핑 | 비대칭 차로 연결·보행 허용 검사, 실제 이동 |

| 같은 입력인데 이전 결과 경고 | 정수 2와 소수 2.0 직렬화 해시 차이 | 숫자 정규화, 기존 설정 재비교 테스트 |
| 교차로 SVG가 보이지 않음 | HTML 표시 방식의 SVG 처리 | 이미지 표시로 변경 후 실제 브라우저 확인 |

| 기본값 복원 후 화면과 계산값 불일치 | 위젯 키 삭제 대신 기본값을 명시적으로 대입 | 다른 입력을 다시 바꿔도 기본값이 유지되는 회귀 테스트·화면 확인 |

OneDrive 오류는 docs/onedrive_failure.log, UI 오류는 docs/ui_float_failure.log에 보존했습니다. 실패 기록은 성공 결과로 포장하지 않습니다. 소스 해시는 각 실행 당시 값이므로 수정 전·후 묶음에서 다를 수 있습니다. 최종 UI의 1시간 재실행과 기본 연구 결과의 비교는 docs/reproduction_audit.json으로 남깁니다.

## 11. 해결하지 않은 한계

- 좌·우회전, 여러 교차로의 연동, 버스·트럭, 주차장 출입구, 상류 유출입을 모델링하지 않았습니다.
- 아파트 발생교통량·방향 분배는 직접 입력하는 가상 값이며 도시별 실제 개발 교통량을 예측하지 않습니다.
- 공식 포화교통류율·출발 손실과 SUMO 차량 동작 사이 현장 보정이 없습니다.
- 보행은 일정 속도·낮은 수요·짧은 진입 허용 등 단순 가정입니다. 무단횡단, 휠체어·유모차 행동, 보행 군집을 검증하지 않았습니다.
- 정지 차량 대수만 관측하며 E2 기반 대기행렬 길이와 공식 LOS는 구현하지 않았습니다.
- 과포화 시 추가 종료시간에 따라 완료 비율이 달라집니다. 미완료가 많은 실험의 평균 시간만 최적화하면 안 됩니다.
- 5개 시드의 합성 반복은 현장 통계적 효과의 증거가 아닙니다. 교차로·수요·매개변수를 바꾼 외부 검증이 필요합니다.
- 로컬 단일 사용자 앱입니다. 브라우저 새로고침 뒤 이전 작업 제어, 다중 사용자 작업 큐, 서버 배포는 구현하지 않았습니다.
- 생성 도로망은 도식적이며 입력 가정 횡단길이를 실제 형상에 강제로 반영하지 않습니다.
- 전문가/동생분의 실무 검토는 아직 수행 사실을 확인하지 않았습니다.

## 12. 후속 연구의 순서

다음 단계는 기능 수를 늘리기보다 검증 자료를 확보하는 것입니다. 먼저 동생분이 실무와 다른 가정을 표시하고, 공개 또는 사용 허가된 한 교차로의 차로·신호·교통량 자료를 확보합니다. 자료 출처·기간·사용 조건을 기록하고, 보정용/검증용을 나눈 뒤 차종·차두간격 등 SUMO 동작을 보정합니다. 이후 횡단 형상과 실제 보행시간, 대기행렬 관측치, 주변 교차로 영향을 차례로 추가합니다. 현장 신호 적용은 별도 전문가 검토와 적법한 절차의 범위입니다.
